---
title: Automatic cleanup
description: Scheduled prune of images, volumes, containers and build cache
---

Deploying continuously fills a disk: every build leaves images behind, every recreated container leaves a stopped one, and BuildKit's cache grows forever. Nexploy can run a **scheduled prune** to reclaim that space on its own.

Configured from **Administration → Settings**, next to the disk usage card that shows what each category currently costs.

## What it prunes

Pick the categories to include — each one maps to a Docker prune:

| Target | Default | What it removes |
|---|---|---|
| **Containers** | enabled | Every stopped container |
| **Images** | enabled | Every **unused** image, not just dangling ones |
| **Build cache** | enabled | The BuildKit build cache |
| **Volumes** | disabled | Every volume not attached to a container |

<Callout type="warn" title="Images and volumes are the dangerous two">
  Image cleanup removes any image no container is running — including the images your past [versions](/en/core-concepts/versions) point to, which makes those rollbacks fail. Volume cleanup removes unattached volumes, which is where a database of a stopped stack lives. Both are opt-in decisions, not defaults to accept blindly; volumes are disabled out of the box for that reason.
</Callout>

The same four prunes are also available as pipeline nodes — `prune-containers`, `prune-images`, `prune-volumes` and `prune-build-cache` — when you would rather reclaim space at a precise point in a build than on a daily schedule. See the [node catalogue](/en/pipelines/node-types).

## Scheduling

Cleanup runs **once a day**, at the hour you choose (UTC). It is driven by an Inngest function that sleeps until the scheduled hour, runs the selected prunes in order, then re-schedules itself — so there's no cron to install and a missed run doesn't pile up.

Settings are re-read right before the prune executes: disabling cleanup cancels the run that was already waiting, and it takes effect immediately.

The schedule is **per Docker environment** — each host has its own settings and its own cycle, so you can prune aggressively on a build host and leave production alone.

## Reporting

After each run, Nexploy records when it ran and how much disk space was reclaimed, both shown in the settings card. A run where no category is selected does nothing and reclaims nothing.

## Disk space guard

The prune reclaims space once a day; the **disk space guard** keeps the server from filling its disk between two runs. It is configured from **Administration → Settings**, next to the cleanup card.

| Setting | Default | Effect |
|---|---|---|
| **Enable the disk guard** | on | Without it, no operation is ever refused |
| **Warning threshold (%)** | `80` | Above it, an alert is recorded in the activity log, without blocking anything |
| **Blocking threshold (%)** | `90` | Above it, every space-consuming operation is refused. Must be higher than the warning threshold |
| **Minimum free space (MB)** | `2048` | Below it, operations are refused too, whatever the percentage |

Once the blocking threshold is reached, these operations answer `507` with the code `DISK_SPACE_LOW`: container create, recreate, migrate and ephemeral run, image `pull`, `import`, `load` and mirror, volume create and cache restore, backup restore, compose stack deploy and migrate, pipeline deployments and builds. Reading, stopping and deleting still work — enough to make room.

Disk usage is read again **every ten minutes**: moving into warning or blocking is recorded once in the [activity log](/en/security/activity-log) under `diskGuard.warning` or `diskGuard.blocking`, and going back to normal clears the alert. The disk measured is the one holding the `DISK_GUARD_PATH` path — see [Environment variables](/en/reference/environment-variables).
