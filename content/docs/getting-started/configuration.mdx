## Variables d'environnement principales

| Variable | Rôle |
|---|---|
| `DATABASE_URL` | Chaîne de connexion PostgreSQL |
| `ENCRYPTION_KEY` | Secret dont dérive (scrypt) la clé AES-256-GCM de chiffrement des variables d'env — sans défaut, à générer avec `openssl rand -hex 32` |
| `BETTER_AUTH_SECRET` | Secret d'authentification — sans défaut, à générer avec `openssl rand -hex 32` |
| `BETTER_AUTH_URL` | URL publique de l'application |
| `DOCKER_API_URL` | URL du service `docker-api` |
| `NEXPLOY_API_KEY` | Clé partagée entre les deux services — **nexploy** l'envoie à `docker-api`, qui l'attend et l'utilise pour rappeler nexploy. Même nom de variable et même valeur dans les deux `.env`, générée par `pnpm db:seed` |
| `INNGEST_BASE_URL` | URL du serveur Inngest self-hosté |
| `INNGEST_EVENT_KEY` | Clé d'événement Inngest |
| `INNGEST_SIGNING_KEY` | Clé de signature Inngest |
| `LOG_LEVEL` | Niveau de log (ex. `info`) |

<Callout>La liste complète est disponible dans `apps/nexploy/.env.example` et `apps/docker-api/.env.example`.</Callout>

En production, l'installeur (`install.sh`) génère automatiquement tous ces secrets et les passe directement à chaque conteneur au démarrage (`docker inspect nexploy_app` pour les consulter) — rien n'est écrit dans un fichier sur l'hôte. En développement, `BETTER_AUTH_SECRET` et `ENCRYPTION_KEY` doivent être générés manuellement, tandis que `NEXPLOY_API_KEY` est produite par `pnpm --filter=nexploy db:seed` — voir [Installation](/getting-started/installation) pour le détail.

## Premier démarrage

Au premier lancement, l'application vous redirige vers `/setup` où vous créez votre compte administrateur. Vous pourrez ensuite :

1. Connecter un **provider Git** (GitHub, GitLab, Gitea, Bitbucket ou Azure Repos). Un dépôt public peut aussi être ajouté par URL, sans provider — il est enregistré sous le provider `CUSTOM`.
2. Configurer un ou plusieurs **environnements** (hôtes Docker).
3. Créer votre premier **dépôt** à déployer.
