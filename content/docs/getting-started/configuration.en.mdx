## Main environment variables

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | PostgreSQL connection string |
| `ENCRYPTION_KEY` | AES-256-CBC encryption key (32 hex bytes) for env variables — no default, generate with `openssl rand -hex 32` |
| `BETTER_AUTH_SECRET` | Authentication secret — no default, generate with `openssl rand -hex 32` |
| `BETTER_AUTH_URL` | Public URL of the application |
| `DOCKER_API_KEY` | Key **nexploy** sends to `docker-api` to authenticate — generated by `pnpm db:seed` |
| `NEXPLOY_API_KEY` | Key **docker-api** expects (on the `docker-api` side, same value as `DOCKER_API_KEY`) and uses to call nexploy back |
| `INNGEST_BASE_URL` | URL of the self-hosted Inngest server |
| `INNGEST_EVENT_KEY` | Inngest event key |
| `INNGEST_SIGNING_KEY` | Inngest signing key |
| `LOG_LEVEL` | Log level (e.g. `info`) |

<Callout>The full list is available in `apps/nexploy/.env.example` and `apps/docker-api/.env.example`.</Callout>

In production, the installer (`install.sh`) generates all of these secrets automatically and passes them directly to each container at startup (`docker inspect nexploy_app` to view them) — nothing is written to a file on the host. In development, `BETTER_AUTH_SECRET` and `ENCRYPTION_KEY` must be generated manually, while `DOCKER_API_KEY`/`NEXPLOY_API_KEY` are produced by `pnpm --filter=nexploy db:seed` — see [Installation](/getting-started/installation) for the details.

## First launch

On first launch, the app redirects you to `/setup` where you create your administrator account. You can then:

1. Connect a **Git provider** (GitHub or GitLab).
2. Configure one or more **environments** (Docker hosts).
3. Create your first **repository** to deploy.
