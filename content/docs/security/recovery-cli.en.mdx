---
title: Recovery CLI
description: Reset an admin password when the app is down, via @nexploy/cli
---

`@nexploy/cli` is a command-line tool that acts **directly on the instance's
Postgres database** — not through the application's API. It therefore still
works even if `nexploy_app` is down, misconfigured, or its admin password is
lost.

<Callout type="warn" title="Run on the server, as root">
It needs access to the Docker socket (`docker inspect`) and reads
`/etc/nexploy/cli.env` (generated by `install.sh`) — it can't be used outside
the machine where Nexploy is installed.
</Callout>

## Install

```bash
npm install -g @nexploy/cli
```

Requires Node.js ≥ 18 and Docker on the server.

```bash
nexploy --version
```

## How it reaches the database

No password is ever stored on disk by the CLI. On every run, it reads the
Postgres password and the container's address directly via
`docker inspect nexploy_postgres` — the same data Nexploy itself used to
start that container, never duplicated elsewhere.

Concretely, it's equivalent to:
```bash
docker inspect nexploy_postgres --format '{{json .Config.Env}}'          # POSTGRES_PASSWORD, etc.
docker inspect nexploy_postgres --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'  # IP address
```
then connects directly to `postgresql://nexploy:<password>@<ip>:5432/nexploy`.

<Callout type="warn" title="The CLI needs Docker">
If `docker inspect nexploy_postgres` fails (Docker missing, container
stopped, no permission on `/var/run/docker.sock`), the CLI reports it
explicitly instead of failing silently.
</Callout>

## Configuration

Nothing to configure by hand for database access — see above. The only file
the CLI reads is `/etc/nexploy/cli.env`, generated by `install.sh`, which
only contains:

| Variable | Role |
|---|---|
| `NEXPLOY_CLI_KEY_HASH` | SHA-256 hash of the recovery key |

That's a non-reversible hash (not a plaintext secret) — it's the only piece
of data the CLI needs to store on the host, since it runs outside Docker and
must be able to verify the recovery key even if no container is responding.
Override with `NEXPLOY_DIR` if Nexploy was installed elsewhere.

<Callout title="Earlier installations">
Installations from before this change had an `/etc/nexploy/nexploy.env`
containing every secret (database, Better Auth, encryption, etc.). The next
`upgrade` automatically migrates the recovery key hash into `cli.env` and
removes the old file — nothing to do manually.
</Callout>

## Recovery key

Every command requires the **recovery key** shown once when Nexploy was
installed. It's prompted for interactively, or can be passed
non-interactively via `NEXPLOY_CLI_KEY`:

```bash
NEXPLOY_CLI_KEY="<key>" sudo -E nexploy admin reset-password
```

If you lost it, generate a new one on the server:

```bash
curl -fsSL https://nexploy.app/install.sh | sh -s rotate-cli-key
```

<Callout type="warn">
The plaintext key is shown only once during rotation — only its hash
(`NEXPLOY_CLI_KEY_HASH`) is stored afterward. The old key stops working
immediately.
</Callout>

## Commands

### `nexploy admin reset-password [--email <email>]`

Resets a user's password to a freshly generated random one, and revokes all
of their active sessions. Without `--email`, targets the single user with
the `admin` role — pass `--email` if there's more than one admin, or to
target a non-admin account.

```bash
sudo nexploy admin reset-password
```

<Callout type="warn">
Only works for accounts with an email/password login — the only way to sign in
to Nexploy, so the normal case. An account with no `credential`-type `account`
row makes the command fail explicitly, rather than creating a password on an
account that doesn't use one.
</Callout>

### `nexploy security unpublish-database [--dry-run] [--skip-backup] [-y]`

Instances installed before `@nexploy/cli` v0.1.9 published Postgres on
`127.0.0.1:5432`. That binding is loopback-only — it was never reachable from
the network — but nothing uses it: `nexploy_app` connects over the Docker
network (`nexploy_postgres:5432`), and the CLI connects to the container's
bridge IP.

This command removes it by recreating `nexploy_postgres` with the same image,
environment, networks, labels, healthcheck and restart policy, minus the
published port. The named volume is reattached, so **no data is lost**.
`nexploy_app` is stopped before and started again after.

```bash
sudo nexploy security unpublish-database --dry-run   # show the plan only
sudo nexploy security unpublish-database
```

A `pg_dump` is written to `<NEXPLOY_DIR>/<db>-pre-unpublish-<timestamp>.dump`
(`0600`) first, unless `--skip-backup` is passed.

<Callout title="Aborts rather than guess">
The command stops before touching anything if the dump fails, if the data
lives in an anonymous volume (which would not survive recreation), or if the
container is managed by Docker Compose — in that case it prints the
`docker compose up -d --force-recreate` steps to run instead. Re-running it
once the port is gone is a no-op.
</Callout>

## Audit log

Every `admin` and `security` action (success **or** failure — invalid key, user not found,
etc.) is appended as a JSON line to `<NEXPLOY_DIR>/cli-audit.log` (default
`/etc/nexploy/cli-audit.log`), root-only (`0600`). Each entry records a
timestamp, host, OS user, action, outcome, and target — never the generated
password itself.

```json
{"timestamp":"2026-07-21T12:52:04.075Z","host":"ubuntu-4gb-nbg1-1","user":"root","pid":15174,"action":"admin.reset-password","outcome":"success","target":"admin@example.com"}
```

## Why direct database access instead of an API call

`@nexploy/cli` is deliberately built as a last-resort tool: it bypasses the
application to stay usable even when it's down or unreachable. Application
secrets (Postgres password, encryption keys, etc.) live only in the Docker
containers' own environments — never duplicated into a file on the host. The
only thing the CLI stores itself is a non-reversible hash of the recovery
key, which should still be treated as an infrastructure-level secret.
