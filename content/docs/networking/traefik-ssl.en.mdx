Nexploy uses **Traefik** as a reverse proxy.

- **Automatic routing** — each repository gets its own router/middleware config.
- **Automatic HTTPS** — Let's Encrypt certificates generated and renewed automatically.
- **Custom certificates** — you can also provide your own SSL certificates, see [SSL certificates](/en/networking/ssl-certificates).
- **Traefik dashboard** available to inspect the routes.

## Configuration on startup

Traefik's configuration (dynamic rule files and static config) isn't shipped statically: `nexploy` generates it itself on startup if it doesn't already exist — never if it does, so a manual customization is never overwritten. This same mechanism powers both an `install.sh` install and a `docker-compose` deployment.

## IP or domain for the instance itself

If you installed Nexploy without a domain (IP mode, see [Installation](/getting-started/installation)), the instance runs over plain HTTP, with no certificate. You can switch to a real domain with HTTPS at any time from **Admin → Settings**: enter the domain and a Let's Encrypt email, then save. Nexploy recreates its own container with the new settings and restarts Traefik automatically — expect a few seconds of downtime, no reinstall or manual file editing required.

This switch is only available for instances installed via `install.sh` — not for a `docker-compose` deployment, where the domain is fixed once and for all in the compose file.

<Callout type="warn">
This address change (IP → domain, or the reverse) changes the instance's base URL. The **redirect (callback) URL** of your OAuth app on the git provider still points to the old address and must be updated **manually**: no provider exposes an API to change it.
</Callout>

**Webhooks**, on the other hand, are re-propagated automatically on save, across every repository that has one: the GitHub App's webhook URL is rewritten, GitHub, GitLab and Gitea webhooks are edited in place, and Bitbucket and Azure Repos ones — whose API offers no update — are recreated. The outcome is recorded in the [activity log](/en/security/activity-log) under `admin.propagateInstanceUrl`, listing the repositories that failed.

After saving, **Admin → Settings** lists the URLs every configured provider expects — OAuth callback, setup redirect, webhook, homepage — each marked "automatic" when Nexploy handles it, with a direct link to the app's settings on the provider.

### Fallback IP

A domain change that goes wrong — DNS not propagated yet, certificate not issued — can leave the instance unreachable, including for rolling the change back. The **fallback IP** field prevents that: when filled in, it adds a second Traefik router over plain HTTP on that IP, serving the same app, alongside the HTTPS router on the domain. The matching origin is also added to the authentication's trusted origins, without which signing in from that address would be refused.

The field only has an effect over HTTPS: in IP mode the instance is already served on its address. It maps to the `NEXPLOY_FALLBACK_IP` variable, set and cleared automatically — see [Environment variables](/en/reference/environment-variables).

### Security headers

The router for the Nexploy app itself goes through a `security-headers` middleware that sets `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, a `Referrer-Policy` of `strict-origin-when-cross-origin` and, over HTTPS only, a one-year HSTS with `includeSubdomains` and `preload`. In IP mode a variant without HSTS is applied instead — pinning HSTS on an IP address would lock out HTTP access to it.

These headers protect the admin interface, not your deployments: the routers generated per repository do not get them. Add them yourself in a repository's Traefik configuration if you need them.
