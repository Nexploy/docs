---
title: Variables d'environnement
description: Référence des variables d'environnement de Nexploy
---

En production via l'installeur (`install.sh`), toutes ces variables sont générées automatiquement et passées directement à chaque conteneur au démarrage — aucune n'est écrite dans un fichier sur l'hôte (consultables via `docker inspect nexploy_app` / `docker inspect nexploy_docker_api`). En développement, elles se configurent dans `apps/nexploy/.env` et `apps/docker-api/.env` (voir [Installation](/getting-started/installation)).

Seul `nexploy-cli` (l'outil de recovery, distinct de l'application) persiste une donnée sur l'hôte, dans `/etc/nexploy/cli.env` : le hash de sa recovery key — voir [CLI de recovery](/security/recovery-cli).

## `apps/nexploy/.env`

| Variable | Rôle |
|---|---|
| `NEXPLOY_URL` | URL publique de l'app (Inngest realtime, appels IA internes, etc.) |
| `NEXPLOY_PORT` | Port d'écoute du serveur Next.js custom (défaut `3000`) |
| `BETTER_AUTH_SECRET` | Secret de signature des sessions — sans défaut, générer avec `openssl rand -hex 32` |
| `BETTER_AUTH_URL` | URL de base utilisée par Better Auth (callbacks/cookies) |
| `TRUSTED_ORIGINS` | Liste d'origines de confiance additionnelles, séparées par des virgules (optionnel) |
| `DATABASE_URL` | Chaîne de connexion PostgreSQL |
| `ENCRYPTION_KEY` | Secret dont dérive (scrypt) la clé AES-256-GCM de chiffrement des variables d'env — sans défaut, générer avec `openssl rand -hex 32` |
| `DOCKER_API_URL` | URL du service `docker-api` |
| `NEXPLOY_API_KEY` | Clé envoyée en `Authorization: Bearer` à `docker-api` pour s'authentifier — générée par `pnpm db:seed`, même valeur que `NEXPLOY_API_KEY` côté docker-api |
| `INNGEST_BASE_URL` | URL du serveur Inngest self-hosté (SDK y envoie les événements / sync les fonctions) |
| `INNGEST_EVENT_KEY` | Clé d'événement Inngest |
| `INNGEST_SIGNING_KEY` | Clé de signature Inngest (vérifie les requêtes entre l'app et le serveur Inngest) |
| `DEPLOYER_WORK_DIR` | Répertoire de travail pour cloner les dépôts et builder les images |
| `TRAEFIK_SERVICE_DIR` | Répertoire hôte du provider fichier Traefik (optionnel, déploiements conteneurisés) |
| `TRAEFIK_CERTS_CONTAINER_PATH` | Chemin des certificats TLS dans le conteneur Traefik (optionnel) |
| `TRAEFIK_STATIC_CONFIG_PATH` | Chemin où écrire `traefik.yml` au premier démarrage si absent (optionnel — n'active le rendu que sur les installs via `install.sh`) |
| `TRAEFIK_USE_TLS` | `false` pour rendre `traefik.yml` sans HTTPS/ACME (mode IP sans domaine) — défaut `true` |
| `ACME_EMAIL` | Email Let's Encrypt utilisé pour rendre `traefik.yml` quand `TRAEFIK_USE_TLS` n'est pas `false` |
| `NEXPLOY_TLS_MODE` | Mode TLS de l'instance : `letsencrypt`, `custom` ou `ip` — à défaut, déduit de `TRAEFIK_USE_TLS` |
| `NEXPLOY_TLS_CERTIFICATE_ID` | Identifiant du certificat téléversé à servir quand `NEXPLOY_TLS_MODE` vaut `custom` |
| `DOCKER_SOCKET` | Chemin du socket Docker de la machine, utilisé comme valeur par défaut du champ *Socket path* des environnements et par `pnpm db:seed` pour l'environnement local. Exposé au navigateur sous `NEXT_PUBLIC_DOCKER_SOCKET` par `next.config.ts`. Défaut `/var/run/docker.sock` — Colima : `~/.colima/default/docker.sock`, Docker Desktop macOS : `~/.docker/run/docker.sock` |
| `TRAEFIK_TEMPLATES_DIR` | Répertoire des templates Traefik utilisés pour rendre `traefik.yml` (optionnel — défaut `<cwd>/traefik-templates`) |
| `HEAP_SOFT_LIMIT_MB` | Seuil de heap en Mo au-delà duquel le serveur déclenche un GC manuel (optionnel — défaut `3200`) |
| `MAX_TURBOPACK_CACHE_GB` | Taille max du cache Turbopack en Go, vidé au démarrage au-delà (développement uniquement — défaut `3`) |
| `LOG_LEVEL` | Niveau de log (ex. `info`) |
| `NODE_ENV` | Mode d'exécution — fixé à `production` par `install.sh` |

## `apps/docker-api/.env`

| Variable | Rôle |
|---|---|
| `PORT` | Port d'écoute (défaut `3300`) |
| `NODE_ENV` | Mode d'exécution — fixé à `production` par `install.sh` |
| `LOG_LEVEL` | Niveau de log |
| `DOCKER_SOCKET` | Chemin du socket Docker à piloter (défaut `/var/run/docker.sock`). Sur Colima ou Docker Desktop macOS, pointez-la sur le socket réel (`~/.colima/default/docker.sock`, `~/.docker/run/docker.sock`) |
| `NEXPLOY_API_URL` | URL de l'app nexploy, pour rappeler l'app |
| `NEXPLOY_API_KEY` | Clé envoyée à l'app nexploy pour s'authentifier (chargement des environnements, synchronisation des suppressions) — même valeur que `NEXPLOY_API_KEY` côté nexploy. Si absente, `docker-api` la récupère au premier appel via `GET /api/internal/docker-api-key` (authentifié par `ENCRYPTION_KEY`) et la garde en mémoire — c'est ce que font les images Docker, ne la fixez pas manuellement dans ce cas |
| `ENCRYPTION_KEY` | Même valeur que côté `apps/nexploy/.env` — envoyée en `x-internal-secret` pour récupérer `NEXPLOY_API_KEY` et faire vérifier par nexploy les clés API reçues |
| `TRAEFIK_CONTAINER_NAME` | Nom du conteneur Traefik à piloter (défaut `nexploy_traefik`) |
| `TRAEFIK_NETWORK_NAME` | Réseau Docker que Traefik surveille (défaut `nexploy_traefik_network`) |
| `NEXPLOY_APP_CONTAINER_NAME` | Nom du conteneur `nexploy_app` (défaut `nexploy_app`) — utilisé pour le recréer lors d'un changement de domaine/IP depuis Admin → Paramètres |
| `TRAEFIK_STATIC_CONFIG_PATH` | Chemin de `traefik.yml`, supprimé puis attendu à nouveau après une recréation du conteneur `nexploy_app` (optionnel) |
| `DOCKER_API_CONTAINER_NAME` | Nom du conteneur `docker-api` (défaut `nexploy_docker_api`) — utilisé lors des mises à jour de l'instance |
| `UPGRADER_CONTAINER_NAME` | Nom du conteneur éphémère qui exécute la mise à jour de l'instance (défaut `nexploy_upgrader`) |
| `NEXPLOY_IMAGE_REPOSITORY` | Dépôt d'images à tirer pour l'app lors d'une mise à jour (défaut `nexploy/nexploy`) |
| `DOCKER_API_IMAGE_REPOSITORY` | Dépôt d'images à tirer pour `docker-api` lors d'une mise à jour (défaut `nexploy/docker-api`) |
| `INNGEST_CONTAINER_NAME` | Nom du conteneur Inngest, redémarré après une mise à jour de l'instance (défaut `nexploy_inngest`) |
| `POSTGRES_CONTAINER_NAME` | Nom du conteneur PostgreSQL, redémarré après une mise à jour de l'instance (défaut `nexploy_postgres`) |
| `NEXPLOY_GITHUB_REPO` | Dépôt GitHub interrogé pour détecter les nouvelles versions (défaut `Nexploy/nexploy`) |

Les variables `SELF_UPGRADE_TARGET_IMAGE`, `SELF_UPGRADE_CONTAINER_NAME`, `SELF_UPGRADE_APP_TARGET_IMAGE` et `SELF_UPGRADE_APP_CONTAINER_NAME` ne se configurent pas : `docker-api` les injecte lui-même dans le conteneur `nexploy_upgrader` qu'il crée pour se mettre à jour, puis ce conteneur les relit au démarrage.

## Conteneur `nexploy_postgres`

Ces variables ne sont lues par aucune des deux applications : elles configurent l'image PostgreSQL elle-même. `install.sh` les passe au conteneur `nexploy_postgres` et compose `DATABASE_URL` à partir d'elles. Lors d'un `upgrade`, il les relit sur le conteneur existant pour ne pas casser la base.

| Variable | Rôle |
|---|---|
| `POSTGRES_DB` | Nom de la base créée au premier démarrage (`nexploy`) |
| `POSTGRES_USER` | Rôle PostgreSQL créé au premier démarrage (`nexploy`) |
| `POSTGRES_PASSWORD` | Mot de passe de ce rôle — généré aléatoirement par `install.sh` (en développement : `nexploy`) |

<Callout type="warn" title="Conservez précieusement votre ENCRYPTION_KEY">
  Elle sert à déchiffrer vos variables d'environnement de dépôt. Sa perte rend vos secrets irrécupérables.
</Callout>

<Callout type="warn" title="NEXPLOY_API_KEY doit être identique des deux côtés">
  C'est le **même** nom de variable et le **même** secret dans `apps/nexploy/.env` et `apps/docker-api/.env`. Un décalage entre les deux fait échouer tous les appels entre les deux services avec une erreur `401`. En production, ne la fixez pas : `docker-api` la récupère auprès de nexploy.
</Callout>

<Callout type="warn" title="ENCRYPTION_KEY doit aussi être identique des deux côtés">
  `docker-api` l'utilise comme `x-internal-secret` pour rappeler nexploy (récupération de sa clé API au premier appel, puis vérification des clés API qu'il reçoit). Une valeur différente casse les deux.
</Callout>
