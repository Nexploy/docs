---
title: Variabili d'ambiente
description: Riferimento delle variabili d'ambiente di Nexploy
---

In produzione tramite l'installer (`install.sh`), tutte queste variabili sono generate automaticamente e passate direttamente a ogni container all'avvio — nessuna viene scritta in un file sull'host (consultabili tramite `docker inspect nexploy_app` / `docker inspect nexploy_docker_api`). In sviluppo si configurano in `apps/nexploy/.env` e `apps/docker-api/.env` (vedi [Installazione](/it/getting-started/installation)).

Soltanto `nexploy-cli` (lo strumento di recovery, distinto dall'applicazione) persiste un dato sull'host, in `/etc/nexploy/cli.env`: l'hash della sua recovery key — vedi [CLI di recovery](/it/security/recovery-cli).

## `apps/nexploy/.env`

| Variabile | Ruolo |
|---|---|
| `NEXPLOY_URL` | URL pubblico dell'app (Inngest realtime, chiamate IA interne, ecc.) |
| `NEXPLOY_PORT` | Porta di ascolto del server Next.js custom (predefinita `3000`) |
| `BETTER_AUTH_SECRET` | Secret di firma delle sessioni — senza valore predefinito, generare con `openssl rand -hex 32` |
| `BETTER_AUTH_URL` | URL di base usato da Better Auth (callback/cookie) |
| `TRUSTED_ORIGINS` | Elenco di origini attendibili aggiuntive, separate da virgole (facoltativo) |
| `DATABASE_URL` | Stringa di connessione PostgreSQL |
| `ENCRYPTION_KEY` | Secret da cui deriva (scrypt) la chiave AES-256-GCM di cifratura delle variabili d'ambiente — senza valore predefinito, generare con `openssl rand -hex 32` |
| `DOCKER_API_URL` | URL del servizio `docker-api` |
| `NEXPLOY_API_KEY` | Chiave inviata in `Authorization: Bearer` a `docker-api` per autenticarsi — generata da `pnpm db:seed`, stesso valore di `NEXPLOY_API_KEY` lato docker-api |
| `INNGEST_BASE_URL` | URL del server Inngest self-hosted (l'SDK vi invia gli eventi / sincronizza le funzioni) |
| `INNGEST_EVENT_KEY` | Chiave di evento Inngest |
| `INNGEST_SIGNING_KEY` | Chiave di firma Inngest (verifica le richieste tra l'app e il server Inngest) |
| `DEPLOYER_WORK_DIR` | Directory di lavoro per clonare i repository e buildare le immagini |
| `TRAEFIK_SERVICE_DIR` | Directory host del provider file di Traefik (facoltativo, deployment containerizzati) |
| `TRAEFIK_CERTS_CONTAINER_PATH` | Percorso dei certificati TLS nel container Traefik (facoltativo) |
| `TRAEFIK_STATIC_CONFIG_PATH` | Percorso in cui scrivere `traefik.yml` al primo avvio se assente (facoltativo — abilita il rendering solo sulle installazioni tramite `install.sh`) |
| `TRAEFIK_USE_TLS` | `false` per renderizzare `traefik.yml` senza HTTPS/ACME (modalità IP senza dominio) — predefinito `true` |
| `ACME_EMAIL` | Email Let's Encrypt usata per renderizzare `traefik.yml` quando `TRAEFIK_USE_TLS` non è `false` |
| `NEXPLOY_TLS_MODE` | Modalità TLS dell'istanza: `letsencrypt`, `custom` o `ip` — dedotta da `TRAEFIK_USE_TLS` se assente |
| `NEXPLOY_TLS_CERTIFICATE_ID` | Identificativo del certificato caricato da servire quando `NEXPLOY_TLS_MODE` vale `custom` |
| `NEXPLOY_FALLBACK_IP` | IP di riserva per raggiungere l'istanza via HTTP mentre viene servita via HTTPS su un dominio — aggiunge un router Traefik su quell'IP e la autorizza come origine attendibile. Impostata e rimossa automaticamente da Admin → Impostazioni, solo mentre TLS è attivo |
| `DOCKER_SOCKET` | Percorso del socket Docker della macchina, usato come valore predefinito del campo *Socket path* degli ambienti e da `pnpm db:seed` per l'ambiente locale. Esposto al browser come `NEXT_PUBLIC_DOCKER_SOCKET` da `next.config.ts`. Predefinito `/var/run/docker.sock` — Colima: `~/.colima/default/docker.sock`, Docker Desktop macOS: `~/.docker/run/docker.sock` |
| `TRAEFIK_TEMPLATES_DIR` | Directory dei template Traefik usati per renderizzare `traefik.yml` (facoltativo — predefinito `<cwd>/traefik-templates`) |
| `HEAP_SOFT_LIMIT_MB` | Soglia di heap in MB oltre la quale il server esegue un GC manuale (facoltativo — predefinito `3200`) |
| `MAX_TURBOPACK_CACHE_GB` | Dimensione massima della cache Turbopack in GB, svuotata all'avvio oltre tale soglia (solo sviluppo — predefinito `3`) |
| `LOG_LEVEL` | Livello di log (es. `info`) |
| `NODE_ENV` | Modalità di esecuzione — impostata a `production` da `install.sh` |

## `apps/docker-api/.env`

| Variabile | Ruolo |
|---|---|
| `PORT` | Porta di ascolto (predefinita `3300`) |
| `NODE_ENV` | Modalità di esecuzione — impostata a `production` da `install.sh` |
| `LOG_LEVEL` | Livello di log |
| `NEXPLOY_DEBUG` | `true` espone le risorse di infrastruttura di Nexploy e rimuove tutte le protezioni associate — **pericoloso**, vedi l'avviso in fondo alla pagina. Impostala anche in `apps/nexploy/.env` |
| `DOCKER_SOCKET` | Percorso del socket Docker da pilotare (predefinito `/var/run/docker.sock`). Su Colima o Docker Desktop macOS, puntalo al socket reale (`~/.colima/default/docker.sock`, `~/.docker/run/docker.sock`) |
| `NEXPLOY_API_URL` | URL dell'app nexploy, per richiamare l'app |
| `NEXPLOY_API_KEY` | Chiave inviata all'app nexploy per autenticarsi (caricamento degli ambienti, sincronizzazione delle eliminazioni) — stesso valore di `NEXPLOY_API_KEY` lato nexploy. Se assente, `docker-api` la recupera alla prima chiamata tramite `GET /api/internal/docker-api-key` (autenticato da `ENCRYPTION_KEY`) e la tiene in memoria — è ciò che fanno le immagini Docker, in tal caso non impostarla manualmente |
| `ENCRYPTION_KEY` | Stesso valore del lato `apps/nexploy/.env` — inviato come `x-internal-secret` per recuperare `NEXPLOY_API_KEY` e far verificare a nexploy le chiavi API ricevute |
| `TRAEFIK_CONTAINER_NAME` | Nome del container Traefik da pilotare (predefinito `nexploy_traefik`) |
| `TRAEFIK_NETWORK_NAME` | Rete Docker che Traefik sorveglia (predefinita `nexploy_traefik_network`) |
| `NEXPLOY_APP_CONTAINER_NAME` | Nome del container `nexploy_app` (predefinito `nexploy_app`) — usato per ricrearlo in caso di cambio di dominio/IP da Admin → Impostazioni |
| `TRAEFIK_STATIC_CONFIG_PATH` | Percorso di `traefik.yml`, eliminato e poi atteso di nuovo dopo una ricreazione del container `nexploy_app` (facoltativo) |
| `DOCKER_API_CONTAINER_NAME` | Nome del container `docker-api` (predefinito `nexploy_docker_api`) — usato durante gli aggiornamenti dell'istanza |
| `UPGRADER_CONTAINER_NAME` | Nome del container temporaneo che esegue l'aggiornamento dell'istanza (predefinito `nexploy_upgrader`) |
| `NEXPLOY_IMAGE_REPOSITORY` | Repository di immagini scaricato per l'app durante un aggiornamento (predefinito `nexploy/nexploy`) |
| `DOCKER_API_IMAGE_REPOSITORY` | Repository di immagini scaricato per `docker-api` durante un aggiornamento (predefinito `nexploy/docker-api`) |
| `INNGEST_CONTAINER_NAME` | Nome del container Inngest, riavviato dopo un aggiornamento dell'istanza (predefinito `nexploy_inngest`) |
| `POSTGRES_CONTAINER_NAME` | Nome del container PostgreSQL, riavviato dopo un aggiornamento dell'istanza (predefinito `nexploy_postgres`) |
| `NEXPLOY_GITHUB_REPO` | Repository GitHub interrogato per rilevare le nuove versioni (predefinito `Nexploy/nexploy`) |

Le variabili `SELF_UPGRADE_TARGET_IMAGE`, `SELF_UPGRADE_CONTAINER_NAME`, `SELF_UPGRADE_APP_TARGET_IMAGE` e `SELF_UPGRADE_APP_CONTAINER_NAME` non si configurano a mano: `docker-api` le inietta da sé nel container `nexploy_upgrader` che crea per aggiornarsi, e quel container le rilegge all'avvio.

## Container `nexploy_postgres`

Queste variabili non vengono lette da nessuna delle due applicazioni: configurano l'immagine PostgreSQL stessa. `install.sh` le passa al container `nexploy_postgres` e compone `DATABASE_URL` a partire da esse. In un `upgrade`, le rilegge sul container esistente per non rompere il database.

| Variabile | Ruolo |
|---|---|
| `POSTGRES_DB` | Nome del database creato al primo avvio (`nexploy`) |
| `POSTGRES_USER` | Ruolo PostgreSQL creato al primo avvio (`nexploy`) |
| `POSTGRES_PASSWORD` | Password di questo ruolo — generata casualmente da `install.sh` (in sviluppo: `nexploy`) |

<Callout type="warn" title="Conserva con cura la tua ENCRYPTION_KEY">
  Serve a decifrare le variabili d'ambiente dei tuoi repository. La sua perdita rende i tuoi secret irrecuperabili.
</Callout>

<Callout type="warn" title="NEXPLOY_API_KEY deve essere identica da entrambi i lati">
  È lo **stesso** nome di variabile e lo **stesso** secret in `apps/nexploy/.env` e `apps/docker-api/.env`. Uno scarto tra i due fa fallire tutte le chiamate tra i due servizi con un errore `401`. In produzione non impostarla: `docker-api` la recupera da nexploy.
</Callout>

<Callout type="warn" title="Anche ENCRYPTION_KEY deve essere identica da entrambi i lati">
  `docker-api` la usa come `x-internal-secret` per richiamare nexploy (recupero della sua chiave API alla prima chiamata, poi verifica delle chiavi API che riceve). Un valore diverso rompe entrambi.
</Callout>

<Callout type="warn" title="NEXPLOY_DEBUG espone l'infrastruttura dell'istanza">
  Nexploy nasconde i propri container (`nexploy_app`, `nexploy_docker_api`, `nexploy_traefik`, `nexploy_postgres`, `nexploy_inngest`, `nexploy_upgrader`), le proprie immagini (`nexploy/nexploy`, `nexploy/docker-api`), le proprie reti (`nexploy_network`, `nexploy_traefik_network`) e i propri volumi (`nexploy_db`, `nexploy_traefik_acme`, `nexploy_deployer_workdir`), e rifiuta ogni rotta che li raggiunga per identificativo.

  `NEXPLOY_DEBUG=true` rimuove tutto: tornano elencabili, ispezionabili e gestibili come qualsiasi altra risorsa. Arrestare `nexploy_postgres`, eliminare `nexploy_traefik_network` o svuotare `nexploy_db` mette l'istanza fuori servizio, e l'eliminazione del volume del database è irrecuperabile.

  Da riservare al debug di un'istanza rotta, su una macchina che puoi permetterti di rompere. Va impostata su **entrambi** i container: `docker-api` applica le protezioni e l'app ne applica una propria.
</Callout>
