---
title: Variables de entorno
description: Referencia de las variables de entorno de Nexploy
---

En producción mediante el instalador (`install.sh`), todas estas variables se generan automáticamente y se pasan directamente a cada contenedor al arrancar — ninguna se escribe en un archivo del host (consultables mediante `docker inspect nexploy_app` / `docker inspect nexploy_docker_api`). En desarrollo se configuran en `apps/nexploy/.env` y `apps/docker-api/.env` (ver [Instalación](/es/getting-started/installation)).

Solo `nexploy-cli` (la herramienta de recuperación, distinta de la aplicación) persiste un dato en el host, en `/etc/nexploy/cli.env`: el hash de su recovery key — ver [CLI de recuperación](/es/security/recovery-cli).

## `apps/nexploy/.env`

| Variable | Función |
|---|---|
| `NEXPLOY_URL` | URL pública de la app (Inngest realtime, llamadas de IA internas, etc.) |
| `NEXPLOY_PORT` | Puerto de escucha del servidor Next.js personalizado (por defecto `3000`) |
| `BETTER_AUTH_SECRET` | Secreto de firma de las sesiones — sin valor por defecto, generar con `openssl rand -hex 32` |
| `BETTER_AUTH_URL` | URL base usada por Better Auth (callbacks/cookies) |
| `TRUSTED_ORIGINS` | Lista de orígenes de confianza adicionales, separados por comas (opcional) |
| `DATABASE_URL` | Cadena de conexión de PostgreSQL |
| `ENCRYPTION_KEY` | Secreto del que deriva (scrypt) la clave AES-256-GCM de cifrado de las variables de entorno — sin valor por defecto, generar con `openssl rand -hex 32` |
| `DOCKER_API_URL` | URL del servicio `docker-api` |
| `NEXPLOY_API_KEY` | Clave enviada en `Authorization: Bearer` a `docker-api` para autenticarse — generada por `pnpm db:seed`, mismo valor que `NEXPLOY_API_KEY` del lado de docker-api |
| `INNGEST_BASE_URL` | URL del servidor Inngest autoalojado (el SDK le envía los eventos / sincroniza las funciones) |
| `INNGEST_EVENT_KEY` | Clave de evento de Inngest |
| `INNGEST_SIGNING_KEY` | Clave de firma de Inngest (verifica las peticiones entre la app y el servidor Inngest) |
| `DEPLOYER_WORK_DIR` | Directorio de trabajo para clonar los repositorios y construir las imágenes |
| `TRAEFIK_SERVICE_DIR` | Directorio host del proveedor de archivos de Traefik (opcional, despliegues contenedorizados) |
| `TRAEFIK_CERTS_CONTAINER_PATH` | Ruta de los certificados TLS en el contenedor Traefik (opcional) |
| `TRAEFIK_STATIC_CONFIG_PATH` | Ruta donde escribir `traefik.yml` en el primer arranque si falta (opcional — solo activa el renderizado en instalaciones mediante `install.sh`) |
| `TRAEFIK_USE_TLS` | `false` para renderizar `traefik.yml` sin HTTPS/ACME (modo IP sin dominio) — por defecto `true` |
| `ACME_EMAIL` | Email de Let's Encrypt usado para renderizar `traefik.yml` cuando `TRAEFIK_USE_TLS` no es `false` |
| `NEXPLOY_TLS_MODE` | Modo TLS de la instancia: `letsencrypt`, `custom` o `ip` — deducido de `TRAEFIK_USE_TLS` si falta |
| `NEXPLOY_TLS_CERTIFICATE_ID` | Identificador del certificado subido que se sirve cuando `NEXPLOY_TLS_MODE` vale `custom` |
| `NEXPLOY_FALLBACK_IP` | IP de reserva para acceder a la instancia por HTTP mientras se sirve por HTTPS en un dominio — añade un router Traefik en esa IP y la autoriza como origen de confianza. Se establece y se elimina automáticamente desde Admin → Ajustes, solo mientras TLS está activo |
| `DOCKER_SOCKET` | Ruta del socket Docker de la máquina, usada como valor por defecto del campo *Socket path* de los entornos y por `pnpm db:seed` para el entorno local. Expuesta al navegador como `NEXT_PUBLIC_DOCKER_SOCKET` por `next.config.ts`. Por defecto `/var/run/docker.sock` — Colima: `~/.colima/default/docker.sock`, Docker Desktop macOS: `~/.docker/run/docker.sock` |
| `TRAEFIK_TEMPLATES_DIR` | Directorio de las plantillas Traefik usadas para renderizar `traefik.yml` (opcional — por defecto `<cwd>/traefik-templates`) |
| `HEAP_SOFT_LIMIT_MB` | Umbral de heap en MB por encima del cual el servidor lanza un GC manual (opcional — por defecto `3200`) |
| `MAX_TURBOPACK_CACHE_GB` | Tamaño máximo de la caché de Turbopack en GB, vaciada al arrancar por encima de él (solo desarrollo — por defecto `3`) |
| `LOG_LEVEL` | Nivel de log (p. ej. `info`) |
| `NODE_ENV` | Modo de ejecución — fijado a `production` por `install.sh` |

## `apps/docker-api/.env`

| Variable | Función |
|---|---|
| `PORT` | Puerto de escucha (por defecto `3300`) |
| `NODE_ENV` | Modo de ejecución — fijado a `production` por `install.sh` |
| `LOG_LEVEL` | Nivel de log |
| `NEXPLOY_DEBUG` | `true` expone los recursos de infraestructura de Nexploy y levanta todas las protecciones asociadas — **peligroso**, ver el aviso al final de la página. Ponla también en `apps/nexploy/.env` |
| `DOCKER_SOCKET` | Ruta del socket Docker a pilotar (por defecto `/var/run/docker.sock`). En Colima o Docker Desktop macOS, apúntala al socket real (`~/.colima/default/docker.sock`, `~/.docker/run/docker.sock`) |
| `DISK_GUARD_PATH` | Ruta cuyo espacio en disco vigila el guardián (por defecto `DEPLOYER_WORK_DIR`, si no `/tmp/deployer`) — ver [Limpieza automática](/es/features/cleanup) |
| `NEXPLOY_API_URL` | URL de la app nexploy, para volver a llamar a la app |
| `NEXPLOY_API_KEY` | Clave enviada a la app nexploy para autenticarse (carga de los entornos, sincronización de las eliminaciones) — mismo valor que `NEXPLOY_API_KEY` del lado de nexploy. Si falta, `docker-api` la recupera en su primera llamada mediante `GET /api/internal/docker-api-key` (autenticado por `ENCRYPTION_KEY`) y la conserva en memoria — es lo que hacen las imágenes Docker, en ese caso no la fijes manualmente |
| `ENCRYPTION_KEY` | Mismo valor que del lado de `apps/nexploy/.env` — enviado como `x-internal-secret` para recuperar `NEXPLOY_API_KEY` y para que nexploy verifique las claves API recibidas |
| `TRAEFIK_CONTAINER_NAME` | Nombre del contenedor Traefik a pilotar (por defecto `nexploy_traefik`) |
| `TRAEFIK_NETWORK_NAME` | Red Docker que Traefik vigila (por defecto `nexploy_traefik_network`) |
| `NEXPLOY_APP_CONTAINER_NAME` | Nombre del contenedor `nexploy_app` (por defecto `nexploy_app`) — usado para recrearlo al cambiar de dominio/IP desde Admin → Ajustes |
| `TRAEFIK_STATIC_CONFIG_PATH` | Ruta de `traefik.yml`, eliminado y luego esperado de nuevo tras una recreación del contenedor `nexploy_app` (opcional) |
| `DOCKER_API_CONTAINER_NAME` | Nombre del contenedor `docker-api` (por defecto `nexploy_docker_api`) — usado durante las actualizaciones de la instancia |
| `UPGRADER_CONTAINER_NAME` | Nombre del contenedor efímero que ejecuta la actualización de la instancia (por defecto `nexploy_upgrader`) |
| `NEXPLOY_IMAGE_REPOSITORY` | Repositorio de imágenes descargado para la app durante una actualización (por defecto `nexploy/nexploy`) |
| `DOCKER_API_IMAGE_REPOSITORY` | Repositorio de imágenes descargado para `docker-api` durante una actualización (por defecto `nexploy/docker-api`) |
| `INNGEST_CONTAINER_NAME` | Nombre del contenedor Inngest, reiniciado tras una actualización de la instancia (por defecto `nexploy_inngest`) |
| `POSTGRES_CONTAINER_NAME` | Nombre del contenedor PostgreSQL, reiniciado tras una actualización de la instancia (por defecto `nexploy_postgres`) |
| `NEXPLOY_GITHUB_REPO` | Repositorio de GitHub consultado para detectar nuevas versiones (por defecto `Nexploy/nexploy`) |

Las variables `SELF_UPGRADE_TARGET_IMAGE`, `SELF_UPGRADE_CONTAINER_NAME`, `SELF_UPGRADE_APP_TARGET_IMAGE` y `SELF_UPGRADE_APP_CONTAINER_NAME` no se configuran a mano: `docker-api` las inyecta él mismo en el contenedor `nexploy_upgrader` que crea para actualizarse, y ese contenedor las relee al arrancar.

## Contenedor `nexploy_postgres`

Ninguna de las dos aplicaciones lee estas variables: configuran la propia imagen de PostgreSQL. `install.sh` las pasa al contenedor `nexploy_postgres` y compone `DATABASE_URL` a partir de ellas. En un `upgrade`, las relee del contenedor existente para no romper la base de datos.

| Variable | Función |
|---|---|
| `POSTGRES_DB` | Nombre de la base creada en el primer arranque (`nexploy`) |
| `POSTGRES_USER` | Rol de PostgreSQL creado en el primer arranque (`nexploy`) |
| `POSTGRES_PASSWORD` | Contraseña de ese rol — generada aleatoriamente por `install.sh` (en desarrollo: `nexploy`) |

<Callout type="warn" title="Conserva cuidadosamente tu ENCRYPTION_KEY">
  Sirve para descifrar las variables de entorno de tus repositorios. Su pérdida hace que tus secretos sean irrecuperables.
</Callout>

<Callout type="warn" title="NEXPLOY_API_KEY debe ser idéntica en ambos lados">
  Es el **mismo** nombre de variable y el **mismo** secreto en `apps/nexploy/.env` y `apps/docker-api/.env`. Un desajuste entre ambos hace fallar todas las llamadas entre los dos servicios con un error `401`. En producción no la fijes: `docker-api` la recupera de nexploy.
</Callout>

<Callout type="warn" title="ENCRYPTION_KEY también debe ser idéntica en ambos lados">
  `docker-api` la usa como `x-internal-secret` para volver a llamar a nexploy (recuperación de su clave API en la primera llamada y luego verificación de las claves API que recibe). Un valor distinto rompe ambas cosas.
</Callout>

<Callout type="warn" title="NEXPLOY_DEBUG expone la infraestructura de la instancia">
  Nexploy oculta sus propios contenedores (`nexploy_app`, `nexploy_docker_api`, `nexploy_traefik`, `nexploy_postgres`, `nexploy_inngest`, `nexploy_upgrader`), sus imágenes (`nexploy/nexploy`, `nexploy/docker-api`), sus redes (`nexploy_network`, `nexploy_traefik_network`) y sus volúmenes (`nexploy_db`, `nexploy_traefik_acme`, `nexploy_deployer_workdir`), y rechaza cualquier ruta que los apunte por identificador.

  `NEXPLOY_DEBUG=true` lo levanta todo: vuelven a ser listables, inspeccionables y manejables como cualquier otro recurso. Detener `nexploy_postgres`, eliminar `nexploy_traefik_network` o vaciar `nexploy_db` deja la instancia fuera de servicio, y eliminar el volumen de la base de datos es irrecuperable.

  Resérvalo para depurar una instancia rota, en una máquina que puedas permitirte romper. Debe estar puesta en **ambos** contenedores: `docker-api` aplica las protecciones y la app aplica una propia.
</Callout>
