---
title: Build pipeline
description: Node graph executed by Inngest on every deployment
---

A deployment doesn't run a fixed list of steps: it executes the **node graph** configured for the stage being deployed, orchestrated by Inngest. Each node is an Inngest step, so the run is durable and streams its logs live.

## What runs

Every stage of a repository has its own pipeline, edited in the [node editor](/en/pipelines/visual-editor). When a build starts, the current graph is **snapshotted** onto the build, so editing the pipeline afterwards never rewrites the history of past builds.

The orchestrator walks the graph, running each node once all of its upstream nodes are done and passing their outputs downstream. A branch whose condition isn't met is marked *skipped*, along with everything after it.

## Starting from a template

Two ready-made templates are available in the editor, to avoid starting from an empty canvas:

| Template | Nodes |
|---|---|
| **Dockerfile** | `clone-repository` → `build-docker-image` → `create-container` |
| **Docker Compose** | `clone-repository` → `validate-compose` → `deploy-compose` → `clean-workdir`, with `save-version` on the side |

Both are just starting points — every node can be added, removed or rewired. The full list is in the [node catalog](/en/pipelines/node-types).

## Build statuses

```
QUEUED → BUILDING → COMPLETED
                  ↘ FAILED / CANCELLED
```

Each node also carries its own status and duration, displayed live on the graph while the build runs.

## Characteristics

- Logs streamed in real time via SSE, per node.
- Cancellable while running.
- A failed build is **not** resumed step by step: the pipeline stops, and re-running it replays the graph from the start.
- Repository environment variables are injected automatically into `deploy-compose` and `create-container`.
